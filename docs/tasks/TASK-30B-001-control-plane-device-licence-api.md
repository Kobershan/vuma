# TASK-30B-001 — Control-plane device and licence APIs

Status: IN_PROGRESS — repository deployable/device-contract foundation implemented  
Stage: 30b  
Type: Separate deployable, application, API, security

## Objective

Create the vendor-owned control-plane boundary for device activation, licence lease refresh,
heartbeat, metering handoff and idempotent device requests. It must not become a tenant trading
dependency or expose tenant business data.

## Why

The existing in-process control-plane double proves licensing behavior but cannot serve real nodes or
provide an independently secured vendor deployment.

## Scope

New `VumaRetail.ControlPlane` deployable, device-facing contracts, replay-safe request identities,
licence issuance through a signer abstraction, lease/heartbeat acknowledgements and health checks.

## Out of Scope

Subscription billing, dunning, abuse/fleet workflows, vendor console, tenant business data access,
and production KMS credentials. Those are TASK-30B-002/003 or deployment configuration.

## Architecture and boundaries

The control plane owns its device registry and audit records. It consumes licensing contracts at the
edge but never opens a tenant database or calls a trading command. Private signing keys are behind
`ILicenceSigner`; no API or model contains key material.

## Dependencies

Stages 04b, 29 and 30; the control-plane API contract and licensing rules.

## Relevant Files

`src/VumaRetail.ControlPlane/`, `docs/API_CONTROL_PLANE.md`, `docs/LICENSING.md`,
`tests/VumaRetail.ControlPlane.Tests/`.

## Implementation Requirements

- Require HTTPS deployment and support mTLS identity at the host boundary.
- Make activation, lease and heartbeat request IDs idempotent.
- Keep licence signing behind an injected external signer.
- Record append-only audit facts without tenant business payloads.
- Return safe errors and never revoke an active licence because the control plane is unavailable.

## Data/Database Impact

Own control-plane persistence only; no tenant migration. The initial implementation may use an
in-memory store for contract tests, but production persistence must be a separate database follow-up.

## API Impact

Adds versioned device routes for activation, lease refresh and heartbeat, plus readiness. OpenAPI is
generated by the separate host.

## Security

mTLS and vendor auth are host/deployment requirements; signer isolation, idempotency and payload
minimization are application requirements. No customer content is accepted.

## Multi-Company/Tenant Impact

Device records are keyed by vendor tenant and node identity. Company identifiers are metadata only and
are never used to query tenant books.

## Sync/Offline Impact

The client treats failed calls as control-plane outage and continues according to its local licensing
ladder. Replayed requests return the original response.

## Acceptance Criteria

- Duplicate activation, lease and heartbeat request IDs return the original result.
- Signer failures produce no licence response and no partial activation.
- A heartbeat carries only allow-listed counters and returns a lease acknowledgement.
- A control-plane health failure has no path to tenant business operations.

## Tests Required

Control-plane unit/API contract tests, signer boundary tests, replay tests, payload allow-list tests,
and a no-tenant-database dependency test.

## Edge Cases

Duplicate requests with changed content, unknown node, expired lease, signer outage, clock skew and
malformed counters.

## Definition of Done

The separate host and tests are committed, its API is documented, and the control-plane project
builds independently of tenant persistence. Production deployment/mTLS/KMS verification remains a
deployment acceptance item.

## Follow-up Findings

Production database, KMS/HSM adapter, certificate provisioning, vendor MFA/RBAC and real-install
acceptance remain for the stage.
