# DECISIONS (ADR log) — Vuma Retail

Every architectural choice lives here. **Decisions marked LOCKED are settled — do not re-open them,
do not "improve" them mid-stage.** New decisions get appended with the next number.

Format: `ADR-NNN — Title — STATUS — one-sentence summary`.

Full rationale (Context/Decision/Consequences) for any ADR: `docs/archive/DECISIONS-ARCHIVE.md` — grep
for the ADR number, e.g. `## ADR-042`.

---

ADR-001 — .NET 9 + WPF for the Windows client — LOCKED — C# 13/.NET 9 with WPF+MVVM for the Windows desktop client; Android is a separate native client, not a shared-UI framework.
ADR-002 — PostgreSQL 16 for store and cloud — LOCKED — Same PostgreSQL 16 engine at both store and cloud tiers, schema-per-module, for identical SQL/migrations and easy restore.
ADR-003 — SQLite offline cache on every terminal — LOCKED — Each Windows terminal keeps a local SQLite cache (catalogue, prices, promotions, customers, outbound queue) so POS never stops even if the LAN or store server is down.
ADR-004 — UUID v7 primary keys — LOCKED — All primary keys are client-generated, time-ordered UUID v7, enabling offline record creation without collisions while keeping B-tree index locality.
ADR-005 — Append-only stock ledger, not a quantity column — LOCKED — On-hand stock is a materialised projection rebuilt from an append-only stock_ledger, not a mutable quantity column, so stock is always explainable and sync-safe.
ADR-006 — Transactional Outbox + idempotent Inbox for all sync — LOCKED — All cross-tier state changes go through a transactional outbox and an idempotent inbox deduplicating on (source_node, operation_id), giving exactly-once effect over at-least-once transport.
ADR-007 — Hybrid Logical Clocks + per-entity conflict policy — LOCKED — Every replicated row carries an HLC stamp; conflict resolution is declared per entity type (LastWriterWins/StoreWins/CloudWins/AppendOnly/ManualReview).
ADR-008 — API-first; the desktop app is just a client — LOCKED — Every capability is exposed via the versioned REST API before any UI is built on it; WPF and Android are both just clients with no private back-channels.
ADR-009 — Hand-rolled CQRS dispatcher, not MediatR — LOCKED — A minimal, self-owned ICommandHandler/IQueryHandler dispatcher with an explicit pipeline (validation→transaction→audit→outbox→logging) replaces MediatR to avoid third-party licensing exposure.
ADR-010 — Modular monolith, not microservices — LOCKED — One deployable store server with strict module boundaries (schema-per-module, no cross-module joins, contracts/domain events only), enforced by an architecture test.
ADR-011 — Velopack for auto-update, WiX for first install — LOCKED — WiX v4 handles first install/prerequisites; Velopack handles all subsequent delta auto-updates for desktop and store server.
ADR-012 — Immutable posted documents — LOCKED — Posted invoices, credit notes, GRNs, stock movements and payroll runs cannot be edited; corrections are new reversing documents.
ADR-013 — Permission model is claim-based and module-scoped — LOCKED — Permissions are module.entity.action strings declared per module; roles are bags of permissions scoped to store(s).
ADR-014 — Tax as a rules engine — LOCKED — Tax groups × jurisdictions × effective-dated rates evaluated per line; VAT rates are seed data, not code.
ADR-015 — Import is a two-phase staged pipeline — LOCKED — File→parse→staging→validate→preview/diff→commit with a reversible batch id and reusable per-source column-mapping profiles.
ADR-016 — Full double-entry financial core, built at Stage 07 — LOCKED — A real GL with chart of accounts, dimensions, periods and a posting-rules engine; modules raise financial events, never name a GL account directly (enforced by architecture test); Finance sits before Inventory/POS.
ADR-017 — Loyalty is its own module with a public API — LOCKED — Loyalty is a separate module with an append-only ledger (balance as projection), configurable earn/burn/tier rules, and a public API for storefronts/apps/partners; points liability posts to the GL.
ADR-018 — Headless commerce: Vuma is the backend of record — LOCKED — A public Storefront API makes Vuma the commerce backend for any frontend, plus an IChannelConnector for existing storefronts/marketplaces/EDI; web orders and web prices always flow through the same Stage 14 order pipeline and Stage 10 pricing engine as the till.
ADR-019 — One workflow, approval, notification and document engine — LOCKED — Built once at Stage 05: approval policies are data, separation of duties enforced centrally via IApprovalService, one unified approval inbox across modules.
ADR-020 — Planning is advisory, never automatic — LOCKED — MRP/DRP output is only a suggestion a human must firm into a real PO/transfer/work order; auto-release is opt-in per item class with a value cap; every suggestion is peggable to its source demand.
ADR-021 — A separate public API host — LOCKED — VumaRetail.PublicApi is a separate host with its own auth (publishable/secret/partner keys, member/customer tokens), rate limits and DTOs; internal fields cannot be serialised by it.
ADR-022 — Statutory boundaries are provider interfaces, not core code — LOCKED — Country-specific e-invoicing, fiscal printers, payment gateways, bank formats and payroll statutory calcs are all provider interfaces with fakes shipped by default; Vuma prepares payroll data but is not a statutory payroll engine.
ADR-023 — Licensing enforces on capability, never on trade or data — SUPERSEDED by ADR-027 — Originally: enforcement escalated through capability restriction (notices→restricted writes→read-only) and never blocked sale/export/backup/DR restore, with a 45-day offline grace ladder; replaced because the vendor's commercial position requires an unpaid subscription to mean no product (its engineering no-accidental-lockout safeguards carried forward into ADR-027/028).
ADR-024 — The control plane is a separate deployment with minimised telemetry — LOCKED — VumaRetail.ControlPlane is a separate deployable with its own DB/credentials/audit log and HSM-held signing key; telemetry is counts/health only (whitelisted, tested); vendor staff need a tenant-granted, time-boxed, dual-audited support grant to see tenant data.
ADR-025 — Vendor billing is separate from tenant finance — LOCKED — The control plane keeps its own subscription/invoice/revenue records entirely separate from any tenant's GL; no cross-visibility either direction.
ADR-026 — Detection over prevention for piracy — LOCKED — Ship reasonable client-side hardening but invest real effort in server-side abuse detection (duplicate fingerprints, counter rollback, clock tamper, etc.) routed to a human-reviewed queue that never auto-disables anything; the real moat is service dependency (cloud backup, sync, updates, Android, public APIs).
ADR-027 — No current licence, no software — SUPERSEDED by ADR-028 (itself superseded ADR-023) — Originally: the app would refuse to open entirely (no POS, no back office, no API, no reporting) on an uncurrent subscription via two paths (cannot-verify tolerance window default 14 days; non-payment after completed dunning), with offline-capable emergency unlock mechanisms; replaced by ADR-028's read-only model because full lockout was found to threaten the business it was meant to protect.
ADR-028 — Lapsed subscription means read-only, not lockout — LOCKED (supersedes ADR-027) — The enforcement ladder ends at read-only (full read/report/reprint/export, no writes including sales); hard lockout survives only as a manual two-person audited vendor action; payment/card-update screens, offline flush and backup stay writable; a vendor-side outage never restricts anyone; recovery is automatic within 60 seconds of payment.
ADR-029 — Involuntary payment failure is a product problem, not a billing problem — LOCKED — Prevent failed charges proactively (expiry reminders, account-updater services, payday-tuned retries, multiple payment methods, in-product/in-email payment-update links); the dunning ladder pauses if notifications aren't confirmed delivered.
ADR-030 — Central package management — LOCKED — Directory.Packages.props at repo root holds every package version; no per-project Version attributes; transitive pinning on.
ADR-031 — Windows-only projects are created by the stage that needs them — LOCKED — Stage 00 creates only the cross-platform skeleton (Domain/Application/Contracts/Infrastructure/Sync/StoreServer/CloudApi/PublicApi + test projects); Desktop/Hardware/Imports/Reporting/ControlPlane/UiTests are created later by the stages that need them, since several target net9.0-windows and cannot build on Linux.
ADR-032 — FluentAssertions pinned to the 6.x Apache-2.0 line — LOCKED — Pinned at 6.12.2 (last Apache-2.0 release) to avoid licence exposure from v8's commercial licence; do not upgrade without buying licences or migrating assertion style.
ADR-033 — Money rounds midpoints away from zero — LOCKED — Money is decimal(18,4), rounded away from zero (not banker's rounding) once at line finalisation, matching South African retail/till expectations.
ADR-034 — Command side-effect classification is mandatory and enforced at build time — LOCKED — Every ICommand<T> must carry [CommandSideEffect(Write|ReadOnly)]; Unclassified is the detectable zero-value default and an architecture test fails the build on it; the three ADR-028 read-only carve-outs are a capped, named ReadOnlyExemption list.
ADR-035 — The concurrency token is an application-generated bytea, not xmin — LOCKED — row_version is an 8-byte app-generated token stamped by AuditInterceptor, not PostgreSQL's xmin, because SQLite terminals have no xmin and the token must survive dump/restore and cross-tier comparison.
ADR-036 — Integration tests bind to a connection string, with Testcontainers as one supplier — LOCKED — PostgresFixture resolves VUMA_TEST_POSTGRES env var, then Testcontainers, then hard-fails with the fix command; never silently skips database tests; scripts/pg-test.sh offers a no-Docker fallback.
ADR-037 — Tenant and Store are platform entities, built in Stage 01 — LOCKED — platform.tenants and platform.stores are built as platform infrastructure in Stage 01 (not a business module), carrying only identity/localisation/activation, so tenant_id/store_id and query filters are meaningful from the first migration.
ADR-038 — ASP.NET Core Identity contributes its hasher, not its stores — LOCKED — Only PasswordHasher<T> (PBKDF2-HMAC-SHA512) is taken from ASP.NET Core Identity; User/Role/Terminal/RefreshToken etc. are ordinary Vuma domain entities driven by command handlers, because IdentityUser/UserManager can't carry the mandatory base-entity columns or fit the pipeline's unit of work.
ADR-039 — ASP.NET Core host wiring lives in VumaRetail.Web — LOCKED — A new project, VumaRetail.Web, holds all ASP.NET-specific wiring (tenant resolution, permission auth handler, terminal cert scheme, auth endpoints) above Infrastructure and below the hosts; PublicApi deliberately does not reference it.
ADR-040 — Authentication is an edge service, not a command — LOCKED — Sign-in/PIN sign-in/refresh/sign-out/terminal auth run through an AuthenticationService outside the command pipeline (so a lapsed read-only tenant can still log in); administrative identity changes remain ordinary Write commands, correctly blocked when read-only.
ADR-041 — POS PINs are unique tenant-wide and resolved per store — LOCKED — A PIN is unique among a tenant's live operators tenant-wide, but sign-in candidates are narrowed to operators holding a role at the terminal's own store, keeping one-gesture sign-on while preventing cross-store sign-in.
ADR-042 — The product is Vuma Retail; code is VumaRetail.*, repo and folder are vuma — LOCKED — Product renamed from Zenith to Vuma Retail across code (VumaRetail.* namespaces/assemblies), runtime identity (Vuma__* config, vuma: claims) and hosting identity (vuma repo/folder); breaking for any existing deployment via the config-section and JWT-claim-type renames; PostgreSQL schema names (module names) were untouched.
ADR-043 — API versioning is URL-segment and hand-rolled — LOCKED — /api/v1/... URL-segment versioning implemented in ~50 lines (VumaApi.MapVumaApi) plus an X-Vuma-Api-Version header, instead of adopting Asp.Versioning.Http.
ADR-044 — The pipeline owns the transaction; handlers do not commit — LOCKED — TransactionBehaviour opens/commits the transaction once around a handler; handlers never call CommitAsync (enforced by two architecture tests), with AuthenticationService and the demo seeder as the only exemptions.
ADR-045 — JWT inbound claim mapping is off — LOCKED — MapInboundClaims = false so claims are read under their issued names (sub, vuma:*) rather than being rewritten into legacy WS-Federation URIs; fixed a live bug where every FindFirstValue("sub") returned null.
ADR-046 — The audit stamp is applied before the outbox serialises, not at SaveChanges — LOCKED — Audit stamping moved into a shared AuditStamper called by both the outbox behaviour (before serialisation) and the interceptor (as a fallback), fixing blank created_by/created_at on replicated rows; rows applied from a peer are not re-stamped, preserving the originating node's identity.
ADR-047 — A bad operation is rejected alone, never with its batch — LOCKED — The sync receiver catches DomainException per operation and records it as Rejected on that operation only; infrastructure failures (connection drop, deadlock, timeout) still roll back the whole batch for retry.
ADR-048 — VumaRetail.Sync sits below Infrastructure, not beside it — LOCKED — Sync references only Application/Contracts (no EF/HTTP/S3); Infrastructure references Sync and supplies the adapters, making the replication protocol (HLC, conflict resolver, receiver, dispatcher) testable in-process and reusable across terminal/store/cloud.
ADR-049 — The hybrid logical clock stamp is a base-entity column — LOCKED — Entity.SyncStamp is a mandatory column (sortable string) written by the outbox behaviour locally and copied verbatim (never re-stamped) by the replica writer on remote application, so ADR-007's conflict policies actually have a comparable value to read.
ADR-050 — Ed25519 comes from BouncyCastle — LOCKED — BouncyCastle.Cryptography (MIT, pure managed) supplies Ed25519 for licence/lease/emergency-code signatures, avoiding NSec's native libsodium dependency inside a WPF till/WiX bundle; production private keys live in a KMS, never in-process.
ADR-051 — VumaRetail.Licensing sits below Infrastructure, and ships a development key pair — LOCKED — A new project on the ADR-048 pattern (Application/Contracts only) holds the enforcement ladder, signed-document format, entitlement choke point, InProcessControlPlane fake, and a compiled-in dev Ed25519 key pair that the store server refuses to start on outside Development.
ADR-052 — The read-only exemption set stays three kinds; membership is a closed list — LOCKED — The ADR-034 cap of three stays on exemption kinds (not command count); ReadOnlyExemption.Payment is read broadly to cover the whole licence/payment screen including withdrawing (but never granting) a vendor support-access grant.
ADR-053 — Fingerprint tolerance scales with what the machine can report — LOCKED — The hardware-match threshold is 7-of-11 weighted points when all five components are captured, and the same proportion when fewer are captured (since WMI/registry components aren't available cross-platform), always erring toward tolerant rather than a false rebind demand.
ADR-054 — CurrentLevel moves off IEntitlementService onto IEnforcementStatusReader — LOCKED — The enforcement-level getter moved to a new IEnforcementStatusReader interface so "no query handler depends on IEntitlementService" (the read-only-gates-no-reads rule) is enforceable by type rather than by a reviewed exception list.
ADR-055 — Money held for customers is a liability with its own module — LOCKED — Credit accounts, lay-bys and stokvels are one module (Stage 10b); deposits/contributions post to liability accounts and release to revenue only on delivery; lay-by/stokvel stock is reserved (not sold, no revenue/cost of sale) until final payment; stokvel benefits are time-weighted by contribution.
ADR-056 — Vuma Connect: both sides are tenants, and a supplier never writes into a retailer — LOCKED — A supplier is a full Vuma tenant; trading happens over mutually accepted, revocable connections; every cross-tenant data flow (including published prices) lands as a proposal the receiving side must accept, never a silent update; cross-tenant isolation gets a dedicated security suite.
ADR-057 — Vuma orchestrates payments, it does not hold funds — LOCKED — Money moves through a licensed provider behind IPaymentGateway/ISettlementProvider; Vuma orchestrates/records/reconciles (retailer AP, supplier AR) without becoming a payments institution; both interfaces ship with fakes.
ADR-058 — One design system, generated from one token file — LOCKED — design/tokens.json is the single source of truth; WPF/Compose/CSS theme files are generated in CI (hand-edits fail the build); an architecture test scans for literal hex values; dark defaults on POS, light in back office.
ADR-059 — Unattended operation is a first-class requirement — LOCKED — AskUserQuestion is denied, .claude/** writes are forbidden, bypass mode is set at launch, and run-autonomous.ps1 runs one stage per invocation verifying three independent progress signals before continuing.
ADR-060 — A variant's attributes are one ordered jsonb column, not a child table — LOCKED — ItemVariant.Attributes is an ordered value-object list mapped to a single jsonb column (with a registered value comparer) rather than a normalised child table, since variant dimensions are few and never queried by attribute value in this product.
ADR-061 — A barcode is the one entity in this stage that is genuinely hard-deleted — LOCKED — RemoveBarcodeCommand does a real DbSet.Remove (not soft delete) because a barcode carries no history of its own and must free its value for reuse; removing a primary barcode atomically promotes a sibling.
ADR-062 — Item and partner counts get no LimitKind; they stay unlimited — LOCKED — No LimitKind.Items/Partners is added to LICENSING.md's closed limit list; catalogue size is never plan-gated unless a future ADR explicitly revises the licensing document.
ADR-063 — The daily reconciliation check is a plain IHostedService, not a Quartz job — LOCKED — FinanceReconciliationHostedService is a simple 24-hour BackgroundService issuing the same command a manual "check now" click would, rather than a Quartz job, since schedules aren't tenant-configurable and a missed pass costs nothing.
ADR-064 — Finance is a core module, not a licensable one — LOCKED — FinanceModuleManifest.IsCore is true and cannot be switched off, because every other module (POS included) posts through it; selling "accounting" as a tier would gate UI/permissions only, never the posting engine.
ADR-065 — Document number counters are node-local and locked inside the caller's transaction — LOCKED — DocumentNumberCounter is NodeLocal (never replicated, since a printed number can't wait for consensus) and takes a SELECT...FOR UPDATE lock inside the caller's own transaction so a rejected posting never burns a number.
ADR-066 — Journal.Lines is a backing-field one-to-many, not an owned collection — LOCKED — JournalLine is a full entity (own audit columns, own sync stamp, individually referenceable by bank reconciliation) mapped as a plain one-to-many over a backing field, not an EF owned collection, while immutability is still enforced by Journal.Post.
ADR-067 — An optional Money is two plain columns and a computed accessor, never a complex property — LOCKED — Because EF Core 9 cannot configure a complex property as optional (a model-build-time failure, not a compile error), an optional monetary amount is {name}Amount/{name}Currency plain columns plus a computed Money? accessor; this cost a shipped commit that made VumaRetailDbContext throw on construction.
ADR-068 — Stock is valued at weighted-average moving cost — LOCKED — Every receipt blends into StockBalance.AverageCost; every issue relieves at that average; no cost layers, no lot tracking, no revaluation pass — the simplest defensible method, with lot/FIFO costing deferred as an additive later change.
ADR-069 — StockBalance is node-local and rebuilt, never replicated as a value — LOCKED — Ledger entries replicate (AppendOnly); the derived StockBalance total does not, because a replicated running total is not safely mergeable and would silently diverge; each node rebuilds its balance from the entries it has applied.
ADR-070 — A missing posting rule does not refuse a stock movement — LOCKED — If Stage 07 has no PostingRule configured for a financial event, the inventory movement still stands and only a warning is logged; refusing the movement would block receiving goods that are demonstrably on the shelf.
ADR-071 — A constructor overload never defaults a parameter that differs only by nullability — LOCKED — General rule: an Entity(Guid id, Guid tenantId, Guid? storeId) overload must not default storeId, because C# overload resolution would silently prefer it over Entity(Guid tenantId, Guid? storeId) for a two-argument non-nullable call, corrupting Id/TenantId with no compiler warning (found via Terminal, costing 14 failing tests).
ADR-072 — A sale line carries the price it was sold at; POS does not resolve prices — LOCKED — SaleLine.UnitPrice is supplied by the caller and stored as sold; POS resolves item and tax but not price, since Stage 10's price list doesn't exist yet and weighed/open-price/manually-reduced lines need caller-supplied prices regardless.
ADR-073 — A stock issue the ledger refuses does not fail the sale — LOCKED — If Stage 08 refuses a stock issue during sale completion, the sale still completes and the line is marked StockIssueStatus.Refused into a manager work queue; only non-business failures (DB fault, cancellation) roll the sale back.
ADR-074 — Stage 10 is split; quotes, invoices and sales analytics become Stage 10c — LOCKED — Stage 10 ships price lists/resolution, promotions and returns (things other stages are blocked on); quotes, invoices and sales analytics move to Stage 10c since nothing in 10c blocks 10b/11/12.
ADR-075 — Tax is computed and stored per line, and no consumer recomputes it from a total — LOCKED — Tax is computed once at line creation and stored; nothing may recompute a document's tax from its total or a historical line's tax at all; sales returns derive tax pro-rata from the original line's stored tax, using cumulative (not per-return) rounding so partial refunds sum exactly.
ADR-076 — A rollback compensates; it never deletes — LOCKED — Import rollback is a compensating operation per row (soft-delete a created row, restore an updated row from a captured before-image, reverse a posted movement with an opposite ledger entry); a row with a missing before-image is refused (IMPORTS_BEFORE_IMAGE_MISSING), never silently skipped.
ADR-077 — The CSV reader is hand-written, not a library — LOCKED — CsvImportSourceReader is a ~200-line hand-written RFC 4180 parser (no CsvHelper) that returns raw strings with no type inference, since type/locale parsing must happen once against the target field's declared type, not twice.
ADR-078 — The command-classification sweep is derived from module manifests — LOCKED — The architecture test enumerating [CommandSideEffect] coverage now sweeps assemblies from registered IModuleManifest implementations rather than a hand-maintained list, so forgetting to register a module fails loudly instead of silently narrowing the sweep.
ADR-079 — An import writes through the domain, never through the DbContext — LOCKED — Import target handlers build entities via the same Create factories and repositories command handlers use (never raw DbContext writes, never calling another command's handler), so every domain invariant protects imported rows too.
ADR-080 — A duplicate row is its own preview verdict, not a kind of valid — LOCKED — A row's preview verdict is exactly one of Valid/Invalid/Skipped (WouldSkip now maps to Skipped, not Valid); fixed a bug where duplicate rows previewed as Valid; BeginCommit now only refuses when there are zero valid-or-skipped rows.
ADR-081 — A purchase order posts nothing to the general ledger — LOCKED — A PO is a promise, not a transaction, and posts nothing; value enters the books at goods receipt and supplier liability crystallises at the three-way match; "committed spend" is a query over open orders, not a GL balance.
ADR-082 — A three-way match is a document, whatever its verdict — LOCKED — SupplierInvoiceMatch is written (201) for every verdict including Blocked, with variances and tolerances snapshotted; only releasing a blocked match can be refused (422), enforced by a DB check constraint.
ADR-083 — Over-receipt is a per-line tolerance, and beyond it the line is refused — LOCKED — A tenant-configured OverReceiptTolerancePercentage (default zero) applies to the cumulative received quantity per order line; deliveries beyond it are refused; comparisons are rounded to avoid decimal-arithmetic false refusals.
ADR-084 — A supplier scorecard is a snapshot over a closed period, never a live figure — LOCKED — SupplierScorecard is a frozen row taken once per supplier per closed period (a still-running period is refused), storing raw counters alongside derived rates; OverallRating is a plain unweighted average since weighting is commercial policy.
ADR-085 — Procurement raises a matched fact; the AP invoice document stays Finance's — LOCKED — Procurement raises a procurement.invoice.matched financial event (with Net/Tax/Gross) rather than creating an ApInvoice itself; Finance's posting rule relieves GRNI and credits trade creditors; a released match is a ledger liability but not yet an AP invoice until Finance raises one.
ADR-086 — Stock is valued at the net cost, never at a tax-inclusive one — LOCKED — PurchaseOrderLine.NetUnitCost (stored Net ÷ quantity, not recomputed via the tax engine) is what goods receipts value stock at, fixing a bug where gross (VAT-inclusive) costs were capitalised into inventory and left VAT permanently stranded in the clearing account.
ADR-087 — A bin id is an additive column on StockLedgerEntry, not a parallel ledger — LOCKED — StockLedgerEntry/StockBalance gain a nullable BinId (default null, backward compatible with every existing call site) instead of a parallel bin-scoped ledger, preserving one source of truth for location-level quantity.
ADR-088 — Bin-to-bin moves get their own append-only ledger, one level below the stock ledger — LOCKED — BinStockMovement is a new append-only, immutable ledger for putaway/pick/internal-transfer moves that redistribute stock inside a location without changing its total; BinStock is its summed projection, posted only through IBinStockMover.
ADR-089 — A cycle count variance posts through IStockLedgerPoster, not only into BinStock — LOCKED — FinalizeCycleCountCommand posts non-zero variances through the existing Stage 08 stock ledger (reusing StockMovementType.StocktakeVariance under a new StockReferenceType.CycleCount) as well as into BinStock, so location-level StockBalance never silently drifts from bin totals.
ADR-090 — Pick allocation is largest-bin-first, behind a strategy interface — LOCKED — IPickAllocationStrategy.Allocate is implemented by LargestBinFirstAllocationStrategy (spills into the next-largest bin only as needed); explicitly not claimed optimal, with the interface seam left for a real slotting/routing engine later.
ADR-091 — Bin capacity is recorded, not enforced — LOCKED — Bin.CapacityValue/CapacityUnitOfMeasure are stored but never checked by any command in this stage, since no bin dimensioning/item cube data exists yet to make enforcement trustworthy; a later stage that adds real dimensioning earns the right to enforce it.
ADR-092 — Order allocation has no reservation ledger of its own; it is read live from PickTask — LOCKED — SalesOrderLine persists only BackorderedQuantity; allocated/fulfilled quantities are computed live from Stage 13's PickTask state via IOrderFulfilmentReader (using the bin allocator's actual result, not a location-level estimate), so there is nothing to reconcile against a second cached number.
ADR-093 — An order return receives stock back at the traced shipment's unit cost, under its own reference type sharing the sales-return movement — LOCKED — CompleteOrderReturnCommand posts via new StockReferenceType.OrderReturn sharing StockMovementType.SalesReturn; unit cost is traced through IOrderFulfilmentReader.GetShipmentUnitCostAsync to the actual ShipmentConfirmation rather than the order line's charged price; an untraceable line completes as Refused rather than inventing a cost basis.
ADR-094 — Order revenue and order returns raise their own financial event types, not a reuse of Stage 09/10's — LOCKED — orders.order.fulfilled and orders.return.completed are new event types with their own posting rules, kept separate from POS/Sales events because timing (once per order vs. per till sale) and target accounts genuinely differ.
ADR-095 — SalesOrderReturn draws from its own ORT document series, never Stage 10's RTN — LOCKED — CreateOrderReturnCommandHandler uses ReturnNumberSeries = "ORT" under ADR-065's gap-free numbering, keeping order returns and till returns unambiguous in an audit trail.
ADR-096 — Revenue is recognised once per order, at completion, not per partial shipment — LOCKED — SalesOrder.RecogniseRevenueIfDue fires once, guarded by IsRevenueRecognised, only once every active line has shipped or been cancelled; a stated v1 simplification, not per-shipment accrual.
